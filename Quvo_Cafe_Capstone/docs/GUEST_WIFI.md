Guest Wi-Fi is a separate admin module. Confirmed admins can edit the exact network name and password through Admin > Guest Wi-Fi. A version check prevents a stale tab from overwriting another admin's update. Passwords are masked in the editor until Show password is selected, and audit events record field names only. Saving updates the customer-facing note; it does not configure the café router.

Run database/24_guest_wifi.sql once before using the editor. This repeatable migration creates a private single-row guest_wifi_settings table with blank initial credentials and preserves all existing orders, payments, guest sessions and accounts. It does not reset previously saved Wi-Fi details when repeated. Wi-Fi is intentionally separate from publicly served website content. Real credentials must be entered by the café; previews and tests use sample values only.

Dine-in tracking includes an expandable Café Wi-Fi note after a cashier-confirmed full payment on any order belonging to the active browser-bound visit. The server verifies the table, active visit token and a full payment record before returning credentials. Unpaid requests never receive a network name or password. Pending/closed visits, another browser's token and inactive tables are denied. A subsequent unpaid order does not revoke an already paid visit's access. Served orders still qualify while the visit remains active, and a new visit at the same table must qualify independently.

The note refreshes alongside normal order polling and can be reopened after a browser refresh. Customers can copy the name/password. Failed Wi-Fi requests clear displayed credentials and offer Refresh Wi-Fi details; ordering and payment continue normally. Ending or changing the visit clears the note immediately and rejects stale request results. Credentials are held in memory/visible fields only and are not put in localStorage or sessionStorage.

The existing guest API exposes view=wifi through the guest session cookie and verified table. The admin API requires staff authentication, admin role, confirmed admin access and the existing CSRF check for writes. Credentials are not added to public/online APIs, order JSON, receipts or history. Application access to a note ends with the visit; the actual router remains responsible for network access.

Validation covers payment gating, own-visit tokens, next visits, admin-only edits, preserved passwords/spaces, concurrent edits, audit contents, public content isolation and repeatable migration using rollback-only local SQL fixtures. Full admin/dine-in browser checks cover responsive layouts, save/reload, conflict drafts, payment unlock, copying, refresh, changes, retry and clearing the note.
